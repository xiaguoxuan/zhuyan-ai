# 住颜 AI：房地产 OPC 90 天路线

> 状态：产品规划草案，仅保存本地，未提交、未推送、未发布。
>
> 核心方向：面向房东、民宿经营者和软装从业者的 AI 房屋焕新与采购工作台。

## 总目标

验证并形成一条可收费、可重复、可交付的业务工作流：

```text
房间照片
→ 软装方案
→ 图片找家具
→ 可编辑采购清单
→ 采购跟踪
→ 多房间项目管理
```

首个垂直场景优先选择：

```text
出租房 / 包租房的低成本软装焕新
```

## 第 1 阶段：验证单房间价值

### 重点功能

- 图片找家具；
- 软装方案生成；
- 四格方案选择；
- 正式效果图；
- 购物清单；
- 固定平台搜索入口；
- 真实照片测试；
- 记录用户修改内容和放弃原因。

### 需要验证的问题

- 用户是否能理解图片找家具的价值；
- 用户是否愿意为一次视觉分析付费；
- 用户最常修改名称、类别、数量还是搜索词；
- 用户是否会实际打开平台搜索；
- 用户是否愿意继续使用软装方案功能；
- 用户愿意为什么结果付费，而不是单纯为模型调用付费。

### 阶段目标

确认客户是否愿意为“可落地的房屋焕新方案”付费，而不只是对生成图片感兴趣。

## 第 2 阶段：做出租房模板

### 产品能力

- 出租房默认约束；
- 低成本焕新目标；
- 尽量保留已有家具；
- 不改结构；
- 不打孔和可逆改造；
- 耐用、易维护的软装方向；
- 多房间统一风格；
- 采购项优先级；
- 必须购买与可选购买区分；
- 购买前实测提醒。

### 适合沉淀的模板

- 包租房客厅焕新；
- 出租卧室快速整理；
- 民宿拍照效果提升；
- 保留大件家具的低成本方案；
- 适合批量复制的房间风格。

### 阶段目标

让一个房东或运营者可以连续处理多套房间，而不需要每次重新设计流程。

## 第 3 阶段：做批量项目和交付

### 产品能力

- 多房间项目；
- 房间编号；
- 统一风格策略；
- 每个房间独立版本；
- 汇总采购清单；
- 重复采购项合并；
- 方案导出；
- 客户分享；
- 采购状态；
- 入住准备任务；
- 维修和交付记录。

### 可交付方案包

```text
房间原图
+ 方案效果图
+ 原图对照
+ 风格说明
+ 保留项和修改项
+ 家具软装清单
+ 逐件搜索词
+ 购买状态
+ 尺寸实测提醒
+ 软装落地注意事项
```

### 阶段目标

从一次图片生成工具升级为持续使用的房屋焕新与运营工具。

## 建议的商业验证方式

早期不急于建设大型平台，优先采用：

1. 单房间按次服务；
2. 图片找家具按次分析；
3. 一套房软装方案与采购清单服务；
4. 多房间批量服务；
5. AI 工具加人工审核和交付。

推荐的早期交付模式：

```text
AI 自动完成约 70%～80%
+
人工负责判断、沟通、校正和最终交付
```

## 关键指标

### 用户价值

- 从上传照片到获得可用结果的完成率；
- 用户完成图片权利确认和费用确认的比例；
- 单张照片平均有效家具条目数；
- 用户编辑和删除条目的比例；
- 搜索入口点击率；
- 清单重新打开率；
- 用户是否实际采购或标记购买。

### 商业价值

- 单房间愿意付费的比例；
- 图片找家具的付费转化率；
- 同一用户处理的房间数量；
- 用户再次使用间隔；
- 单个客户的平均收入；
- 人工审核和交付耗时。

## 需要避免的方向

- 不要只做单次效果图 API 包装；
- 不要一开始同时服务所有房地产人群；
- 不要过早购买 GPU 或自建重模型；
- 不要承诺真实同款、品牌、价格、库存或精确尺寸；
- 不要把 AI 结果当作产权、法律、估价或结构安全结论；
- 不要在没有合规商品数据源前提供未经验证的具体商品详情页；
- 不要省略人工审核、用户确认和版本记录。

## 90 天后的判断标准

如果完成以下条件，说明方向值得继续投入：

- 至少有一类房地产客户持续使用；
- 客户愿意为单房间或单套房方案付费；
- 图片找家具结果能够被用户修正并用于搜索；
- 采购清单比单张效果图更能促成复用；
- 同一客户愿意处理多个房间；
- 人工审核和交付时间可以接受；
- 已经形成出租房场景的默认约束和模板。

## 一句话战略

> OPC 不需要用 AI 做一个庞大的房地产平台，只需要把自己最熟悉的一项房地产服务，变成一个可重复、可交付、可收费的 AI 工作流。

## 长期护城河

住颜 AI 的长期价值不应依赖某一个模型，而应沉淀：

```text
房地产场景知识
+ 房间和项目状态
+ 软装约束
+ 版本历史
+ 采购数据
+ 人工校正
+ 可交付工作流
```
